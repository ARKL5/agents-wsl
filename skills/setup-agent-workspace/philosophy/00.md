# The agent workspace

The user chooses the goal and workflow. Configure the repository so an agent can find the context, use the tools, and check its work.

## Principles

- **Ground in the repository.** Inspect before writing. Distinguish current behaviour from intended behaviour, and observations from decisions.
- **Point before copying.** Name the source and when to read it. Keep procedures at their destination; use short summaries where they save real discovery work.
- **Use consistent names.** Align domain terms and identifiers. Record meaningful mappings to external or legacy names.
- **Keep one authority.** Merge equivalent rules, remove stale material, and move deterministic checks into tools.
- **Fit the purpose.** Reuse working arrangements. Create documents when they have content, and keep project instructions focused on the project.

## What belongs where

| Place | Content |
| --- | --- |
| Project `AGENTS.md` | One-sentence purpose, necessary directory conventions, required-reading triggers, executable verification commands, communication language if needed |
| Machine skill for the repo location (`use-local-windows` or `use-local-wsl`) | Identity, install channels, paths, ports, allowlists |
| `CONTEXT.md` and `docs/adr/` | Glossary and hard-to-reverse trade-offs. `domain-modeling` writes a file when a term or decision crystallises |
| Engineering standards | Implementation and review baseline, plus standing constraints the code cannot explain |
| Code, types, tests, configuration | Executable behaviour and checks |

Keep navigation separate from the rules it points to. The project index keeps pointers to `CONTEXT.md` and `docs/adr/` as the repository's context structure. Engineering standards do not restate the verification command or point at `AGENTS.md`; agents already load that file.

## A working loop

Provide an agent-callable verification command with an exit code and readable output. Reuse existing tooling and make its environment runnable. Report what the checks cover and any gaps.

Code repositories need automated checks, an engineering baseline, and local constraints. Make the baseline reachable before implementation and during review. Adapt the skeletons into project-owned files with local paths; the result should work independently of this skill.
